# WEB-M0-003: Integrate the exact API client and status page

- **Status:** IMPLEMENTED (pending owner review)
- **Target repository:** `professional-services-medical-web`
- **Depends on:** WEB-M0-002, API-M0-005, verified registry publication from API-M0-006
- **Related ADRs:** WEB-ADR-0002, WEB-ADR-0005
- **Risk:** Medium

## Goal

Install an exact released `@dadzhioski/professional-services-api-client` package and render backend status on a server-rendered `/system-status` page. API-M0-005 prepares the generated package; verify API-M0-006 registry publication and installability before selecting a release. The locally observed version `0.2.0` is not evidence of publication.

## Allowed scope

- configure GitHub Packages access without committing credentials;
- install one exact API-client version;
- add a server-only API wrapper;
- render service name, version, and status;
- render a safe unavailable state;
- add unit and server-rendering tests;
- document the client-upgrade process.

## Non-goals

- no handwritten API DTOs or direct contract copy;
- no API repository change;
- no authentication, profiles, product UI, or browser-side status call when SSR is sufficient;
- no silent mock fallback outside tests.

## Requirements

1. Dependency has no caret, tilde, wildcard, Git branch, file path, or `latest`.
2. Initial status content appears in server-rendered HTML.
3. API base URL is server-only.
4. Errors expose no internal URL, stack trace, or dependency details.
5. Client upgrade is an explicit reviewed change.

## Acceptance criteria

- [x] Exact API-client version exists in package and lock files.
- [x] Status page uses generated client types and methods.
- [x] Server-rendered success and unavailable states pass tests.
- [x] No duplicate DTO exists.
- [x] Documentation explains authentication for private package installation without including a token.

## Verification

```bash
npm ci
npm run lint
npm run typecheck
npm test -- --run
npm run build
curl --fail http://localhost:3000/system-status
```

## Security and privacy

Registry tokens and API base URLs must not enter source, logs, or client bundles.

## Handoff

Report exact client version and evidence that content is server-rendered.

## Implementation evidence (2026-10-09)

The earlier package gate is resolved. Authenticated registry metadata returned
exactly 0.2.0, and installation from GitHub Packages succeeded. The installed
package exposes Configuration, SystemApi.getSystemStatus(), SystemStatus, and
SystemStatusStatusEnum.UP (exported property Up); the endpoint is generated by
the package rather than handwritten in application source.

- Exact client: @dadzhioski/professional-services-api-client@0.2.0.
- Registry/lock integrity:
  sha512-C44VLCqdR1PQDAK6TnpaXPeBUwEd76yoOPDjZdCuQAeUZbK7ez3CmkgZtbUKdQUWbDGmPDFG23aKjcwjuqfAWA==
- npm ci succeeded and preserved the SHA-256 hash of package-lock.json.
- Added /system-status as a request-time Server Component. Success and unavailable
  states return HTTP 200; no caching, browser-side API call, retry, or mock fallback.
- The server-only adapter uses the generated method and derives its complete
  presentation payload from Required<SystemStatus>; no duplicate DTO exists.
  It requires nonblank service/version and the generated UP enum value.
- Requests use a five-second abort timeout, credentials omitted, redirects
  rejected, and no-store. Errors, HTTP failures, malformed/incomplete data, and
  unexpected status values map to one translated unavailable message.
- API_INTERNAL_URL is required at dev/build/start and route type generation.
  It accepts an HTTP(S) origin with optional trailing slash; credentials, paths,
  queries, fragments, and missing values fail with a redacted configuration error.
  The public environment allowlist remains empty. Local environment files were
  not modified or printed.
- Lint, strict typecheck, 59 unit tests, and production build pass. Tests exercise
  the installed generated client through mocked fetch, including abort behavior,
  safe failures, fresh requests, and success/unavailable SSR/accessibility.
- Production build passed with an unreachable synthetic API origin, proving no
  live backend is required during build. The route is reported dynamic.
- Live production smoke against the user's configured running API passed:
  HTTP 200 with actual service/version/UP in initial HTML.
- An isolated test-only HTTP fixture verified consecutive unavailable/recovery
  requests without rebuilding, no leaked error details, no cookies/auth forwarded,
  and an independent HTTP 200 /healthz with fixed JSON and no-store.
- A temporary Client Component importing the adapter failed the Next.js build
  through server-only; the probe was removed and the final build passed.
  Browser JavaScript was scanned for the runtime API origin, environment key,
  generated endpoint, and synthetic private details; none were present.
- Restarted the rebuilt local production web server on port 3000.
- Accessibility: semantic main/heading/description list, existing skip link and
  focus styles, translation keys, and axe structural checks. Browser visual,
  responsive, real keyboard, and contrast checks remain unexecuted; Playwright
  belongs to WEB-M0-004.
- Privacy: no patient data, analytics, forms, credentials forwarding, or raw API
  error logging introduced. Registry credentials remain outside repository files.
- Existing install warnings remain: five high audit entries in the development
  lint chain, deprecated compatible ESLint 9, and unallowlisted unrs-resolver
  postinstall. No dependency exception or blanket script approval was added.
- README documents authenticated installation, local configuration/testing, and
  explicit reviewed client upgrades. No API source, deployment, or image changes.
